## 8. Порции (serving)

Поле `serving_size` заполнено у 8 из 15 найденных, но **семантика непоследовательна**: у 4 это реальная порция (Coca-Cola 250 мл, Добрый 250 мл, Увелка 100 г, Bonduelle 100 г), у 4 — вся упаковка как «порция» (Простоквашино 930 мл, Агуша 50 г, Мираторг 300 г, ЭкоНива «1 portion (100 g)»). Встречается внутренняя противоречивость: у Мираторг quantity 100 г при serving 300 г. Для NutriTrack полезнее опираться на расчёт от значений на 100 г/100 мл, а не на serving.

## 11. Заметные несоответствия

1. **Bonduelle кукуруза (3083680002875)** — под российским штрихкодом вернулся венгерский продукт «csemegekukorica» 285 г (запись поддерживается официальным импортёром org-bonduelle-europe-long-life), БЖУ +35% ккал против российской этикетки. Главный риск для приложения: **тот же EAN может нести другой региональный рецепт с другой пищевой ценностью**.
2. **Домик в деревне 950 г** — в OFF размер 925 мл (устаревшая/другая версия упаковки).
3. **Мираторг 300 г** — в OFF quantity «100 g» и countries «Japan» (ложные поля), при этом serving 300 г.
4. **Coca-Cola 900 мл** — в OFF международная запись «1 L» (HBC использует EAN для семейства бутылок 0,9/1 л).
5. **Простоквашино 930 мл** — нет ккал (только кДж); serving = вся упаковка.
6. **Heinz 550 г** — нет имени и размера; идентичность восстанавливается только по бренду + БЖУ.
7. **Увелка** — имя «Buckwheat» (англ.), углеводы 61 против 72 в ритейлер-справочнике (сам справочник может быть неточен).

## 12. Ошибки API и лимиты

- Технических ошибок и срабатываний лимитов **нет**: 20/20 валидных ответов, по одному запросу на штрихкод, последовательные батчи ≤5, без повторов (плюс 2 предпроверочных запроса с заведомо известным штрихкодом).
- Ограничение среды (раскрыто полностью): прямой исходящий трафик песочницы ограничен (GitHub/npm), поэтому запросы к официальному API выполнены через инфраструктуру fetch платформы — те же URL официального API v2, ответы сохранены дословно в `results/off-results.json`. Пользовательский User-Agent из скрипта (`NutriTrackStage7AProbe/1.0`) в этой среде приложен быть не мог — отправлялся UA fetch-клиента. Скрипты в `scripts/source-probe/` запускаемы из любой обычной сети как есть, с правильным UA.
- HTTP-коды напрямую не наблюдались; классификация найдено/не найдено опирается на документированные поля `status`/`status_verbose` самого API (проверено предзапросом: существующий штрихкод → status:1, отсутствующий → status:0 «product not found»).

## 13. Был ли реально протестирован FatSecret

**Нет.** «FatSecret could not be tested because API credentials are unavailable.» Переменные окружения `FATSECRET_CLIENT_ID` / `FATSECRET_CLIENT_SECRET` не заданы; учётные данные не выдумывались, фейковые ответы не создавались. Скрипт `fatsecret-probe.mjs` реализует документированный поток (OAuth 2.0 client credentials → `food/barcode/find-by-id/v1`, region=RU, language=ru; заметка: barcode-endpoint в документации FatSecret помечен как PREMIER) и готов к запуску при появлении ключей. До тестирования с реальными ключами делать выводы о FatSecret нельзя.

## 14. Рекомендуемая архитектура (только на основе измеренного)

Измеренное: 70% повседневных RU-SKU находятся в OFF корректно; при находке бренд точен в 100% случаев, БЖУ полны в 87% случаев и совпадают с этикетками в пределах округления; но 25% SKU отсутствуют, встречаются региональные конфликты рецепта (1/15), ненадёжные метаданные размера/страны, неполные записи, отсутствие ккал при наличии кДж.

1. **Локальная база (273 продукта) остаётся первичным источником** — измеренное покрытие OFF недостаточно для базового сценария «отсканировал обычную покупку → нашёл».
2. **Open Food Facts — опциональный дополнительный источник поиска по штрихкоду** за уже подготовленным в Stage 6 интерфейсом `FoodRepository` (зарезервированные `sourceType: "open_food_facts"`, поля sourceId/verified/imageUrl). Найденный продукт всегда помечается источником («Open Food Facts») и не подменяет молча пользовательские данные.
3. **Обязательные защитные меры парсинга** (продиктованы находками): fallback ккал из кДж (Простоквашино); толерантность к отсутствию name/quantity/фото (Heinz, ЭкоНива, Макфа); НЕ доверять `countries` (Мираторг «Japan») и `quantity` (Домик 925 мл, Мираторг 100 г) — размер упаковки показывать как справочный; расчёт порций от 100 г/мл, а не от serving (непоследовательная семантика); NOT_FOUND → явная деградация на ручной ввод (форма своего продукта уже поддерживает бренд и штрихкод).
4. **Кэшировать ответы по штрихкоду** локально (записи OFF живые, но медленно обновляются; повторы не нужны).
5. **FatSecret не рассматривать**, пока не протестирован с реальными ключами; его barcode-API к тому же платный (PREMIER).
6. Правовое замечание (§13 стадии): страницы ритейлеров использованы только для верификации; копирование их каталогов в NutriTrack не планируется и не проверялось.

## 15. Ограничения проверки

- 20 SKU — небольшой сабординальный набор; смещение в сторону крупных брендов и стабильно продающихся позиций; охват категорий неполный (нет хлеба, заморозки кроме наггетсов и т.п.).
- Один срез времени (2026-09-17); база OFF пополняется (часть записей создана/обновлена в 2025–2026 гг.).
- Референсные БЖУ есть только для 4 найденных SKU (по остальным «unavailable» по правилам стадии).
- Одна запись набора (Алёнка) верифицирована каталогом штрихкодов — отмечено в dataset.json.
- Сравнение Bonduelle «significant» может отражать различие вариантов рецепта, а не ошибку данных (§5D стадии) — расхождение зафиксировано как есть.
